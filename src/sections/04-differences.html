4.2RDBMS ／ DWH との違い：「分解されたデータベース」

RDBMS の構成要素OTF での対応物
データページ／ヒープParquet ファイル（イミュータブル）
WAL ／ redo log_delta_log、Iceberg のスナップショットとメタデータ、Hudi のタイムライン
MVCC のバージョンチェーンスナップショット（ファイル集合のバージョン）
システムカタログカタログ（HMS／Glue／Unity／Polaris／REST）＋テーブルのメタデータ
統計情報ファイル単位の min/max・null 数、Puffin（NDV スケッチなど）
インデックスパーティション、クラスタリング（Z-order／Hilbert）、ブルームフィルタ。本格的なインデックスは Hudi 以外ほぼない
ロックマネージャOCC ＋ ストレージやカタログのアトミック操作
VACUUM ／ チェックポイントコンパクション、expire snapshots、VACUUM
オプティマイザ／エグゼキュータ外部（Spark／Trino／Flink／DuckDB…）。差し替えられる

決定的な違いは粒度とレイテンシです。

RDBMSOTF
並行制御の単位行・ページファイル（MB〜GB）
コミットのレイテンシミリ秒数百ミリ秒〜秒（オブジェクトストレージとの往復）
実用的なコミット頻度毎秒数千〜数万トランザクションテーブルあたり秒〜分単位のマイクロバッチが現実的
点検索インデックスで高速苦手

OTF が（基本的に）提供しないものもあります。

  • OLTP 的な、高頻度で小さなトランザクション
  • 主キー、ユニーク、外部キーといった制約の強制（Delta の CHECK／NOT NULL のように、一部はある）
  • 汎用のセカンダリインデックス
  • 複数テーブルにまたがるトランザクション（Iceberg REST カタログのマルチテーブルコミット、Nessie、DuckLake などで、限定的には可能）

逆に、RDBMS にはない OTF の強みは次のとおりです。

  • ストレージと計算が完全に分離している
  • 同じデータを複数のエンジンで直接読める（データのコピーもエクスポートも不要）
  • ペタバイト級のデータを S3 の単価で保持できる
  • ベンダーが消えても、データはオープン仕様のファイルとして残る

4.3Apache Kudu との違い

KuduOTF
実体常駐の分散サーバ（master ＋ tablet server、Raft）ファイル＋メタデータ（＋カタログ）。サーバ不要
ストレージローカルディスク（3重複製）オブジェクトストレージ
計算と保存密結合分離
更新主キーで行単位の upsert、ミリ秒ファイル単位、コミットは秒〜分
点検索速い苦手
アクセス経路Kudu API 経由（Impala／Spark のコネクタ）どのエンジンもファイルを直接読める
運用クラスタの容量計画、リバランス、障害対応テーブルのメンテナンス（コンパクションなど）
SUMMARY

まとめると、Kudu は「更新レイテンシ」を優先し、OTF は「オープン性・コスト・計算の分離」を優先した設計です。クラウド時代には後者が市場で勝ちました。一方で、ミリ秒単位の更新や点検索が本当に必要な用途は、今でも OTF の守備範囲外です。

4.4クラウド DWH（Snowflake ／ BigQuery）との関係

内部アーキテクチャはよく似ています（イミュータブルな列指向ファイル＋トランザクショナルなメタデータ）。違いは、仕様が公開されているかと、データの所有権が誰にあるかです。現在は DWH 側も Iceberg テーブルを読み書きできるようになり、DWH は「OTF を読み書きするエンジンの一つ」という位置づけに近づいています。Snowflake が Polaris を、Databricks が Unity Catalog を OSS 化したのは、この流れの中でカタログ層の主導権を取りにいく動きと見ることができます。
