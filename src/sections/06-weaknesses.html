弱点と運用上の落とし穴

  1. メンテナンスが必須（「DBA の仕事が自分に戻ってくる」）。小さなファイルをまとめ、古いスナップショットを失効させ、参照されなくなったファイルを消す作業を、誰かが定期的に回す必要がある 代表的なメンテナンス操作 
    -- Delta Lake
OPTIMIZE orders;                       -- 小さなファイルをまとめる
VACUUM orders RETAIN 168 HOURS;        -- 参照されなくなったファイルを物理削除

-- Apache Iceberg（Spark のプロシージャ）
CALL cat.system.rewrite_data_files(table => 'db.orders');
CALL cat.system.rewrite_manifests('db.orders');
CALL cat.system.expire_snapshots(table => 'db.orders', older_than => TIMESTAMP '2024-06-01 00:00:00');
CALL cat.system.remove_orphan_files(table => 'db.orders');
    これを自動化するマネージドな選択肢も増えています（Databricks の Predictive Optimization、S3 Tables の自動コンパクションなど）。
  2. 小さなファイルとメタデータの肥大化。数秒ごとにストリーミングでコミットすると、スナップショット、manifest、小さなファイルが爆発的に増える
  3. 書き込みの競合。OCC なので、同じパーティションに多数の writer が書くとリトライが続発する。writer を分割するなど、設計での回避が必要
  4. エンジン間の機能差。「Iceberg 対応」と書かれていても、v3 の Deletion Vector、equality delete、ブランチ、ビューへの対応はエンジンによってまちまち。「読めるが書けない」こともある
  5. カタログが新たなロックインの源泉になる。フォーマットはオープンでも、アクセス制御やコミットの調停はカタログに依存する
  6. 削除がすぐには物理化されない。タイムトラベルのために古いファイルが残るので、GDPR 対応には expire や VACUUM まで運用に含める必要がある
  7. OLTP やサブ秒の鮮度には向かない。その用途は Postgres などの OLTP DB や KV ストアに任せ、CDC で OTF へ流すのが定石
  8. 「オープン」の度合いは一様ではない。Delta Lake は Linux Foundation の配下だが開発の中心は Databricks で、Iceberg は Apple、Netflix、AWS、Snowflake、Databricks などのコミッターが参加する ASF のプロジェクト。どちらを選ぶかは、ガバナンスの観点でも判断材料になる
