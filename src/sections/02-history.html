02

歴史的経緯

OTF は突然現れたものではありません。Hadoop 以来、「安いストレージに置いた大量のファイルを、どうすればテーブルとして正しく扱えるか」という問題に対して、何度も解き方が試されてきました。まず全体の流れを俯瞰してから、時代ごとに見ていきます。

2.1Hadoop と Hive：「ディレクトリ = テーブル」（2006年〜）

Google の GFS／MapReduce 論文（2003／2004年）をもとに Hadoop が生まれました。MapReduce を Java で書くのはつらいので、Facebook が SQL で書ける Hive を作ります（2008年に OSS 化）。Hive のテーブルモデルは非常に単純です。

Hive テーブルのディレクトリ構成 
/warehouse/sales.db/orders/          ← テーブル = ディレクトリ
    dt=2024-06-01/                   ← パーティション = サブディレクトリ
        part-00000.parquet
        part-00001.parquet
    dt=2024-06-02/
        ...
  • スキーマとパーティションの一覧は Hive Metastore（HMS、裏側は RDBMS）に入る
  • どのファイルがテーブルに含まれるかは、ディレクトリを listing した結果で決まる
  • schema-on-read（読むときにスキーマを当てる）

この単純さと、「HMS さえ読めばどのエンジンからも読める」という開放性のおかげで、Hive、Spark、Presto、Impala などが同じデータを共有できました。HMS と Hive テーブルは事実上の標準になり、OTF の祖先にあたります。OTF が後に解決する問題の多くは、このモデルの限界から生まれています。

2.2列指向ファイルの登場：Parquet と ORC（2013年〜）

テキスト、CSV、SequenceFile、Avro といった行指向の形式は、分析クエリには遅い形式でした。Google の Dremel 論文（VLDB 2010）を受けて、Twitter と Cloudera が Parquet を、Hortonworks と Facebook が ORC を、どちらも2013年に作ります。

主な特徴は次のとおりです。

  • 列単位で読める（projection pushdown）。必要な列だけを I/O する
  • 辞書エンコーディング、RLE／bit-packing、delta encoding、Snappy／ZSTD による圧縮
  • min/max 統計による述語プッシュダウンで、Row Group やページを丸ごとスキップできる
  • Dremel 由来の repetition／definition level で、ネストした構造も列指向で格納できる

ただ、この記事の文脈で重要なのは、Parquet の限界のほうです。

  1. 1ファイルで閉じている。複数のファイルを束ねた「テーブル」の概念がない
  2. イミュータブル。footer が末尾にある構造なので、追記も部分更新もできず、更新は書き直しになる
  3. 統計はファイルを開かないと読めない。ファイルが10万個あれば、footer を読むための GET も10万回かかる
POINT

Parquet はファイル内のスキャン効率を解決しましたが、ファイル群をテーブルとして管理する部分は Hive の素朴なモデルのままでした。この空白を埋めたのが OTF です。また、OTF は Parquet を置き換えるものではなく、Parquet の上に乗るものです。Iceberg、Delta Lake、Hudi のデータファイルは、基本的に Parquet です。

なお、2016年にはメモリ上の列指向形式である Apache Arrow も登場しました。ディスク上は Parquet、メモリ上は Arrow という組み合わせは、いまの分析エンジンの標準的な構成です。

2.3Hive テーブルの限界（OTF が生まれた直接の理由）

  1. 原子性がない。書き込みジョブが途中で落ちると、中途半端なファイルが残って読み手に見える。複数パーティションへの書き込みも非原子的
  2. 分離性がない。書き込み中に読むと途中の状態が見える。INSERT OVERWRITE の最中に、空のパーティションが見えることもある
  3. listing のコスト。クエリ計画のたびに全パーティションのディレクトリを listing する。S3 の LIST は1リクエスト最大1000キーで遅く、数万パーティションだと計画だけで数分かかる。HMS もパーティション数が増えると耐えられない
  4. S3 との相性が悪い
    • Hadoop のコミットプロトコルは「一時ディレクトリに書いてから rename」で原子性を担保していた。しかし S3 の rename は「コピー＋削除」で、遅くて非原子的
    • S3 の LIST は2020年12月まで結果整合性だったので、書いたはずのファイルが見えないことがあった。Netflix は独自の S3 コミッタを作り、AWS は EMRFS で DynamoDB を使って整合性を補っていた
  5. 更新・削除ができない。1行消すのにもパーティションを丸ごと書き直す。GDPR（2018年施行）の削除要求や、CDC の取り込みが非常に重い
  6. スキーマ進化が危険。列を名前か位置で識別するため、次のような事故が起きる（第3章の図も参照）
    • rename すると、古いファイルの列が NULL になる
    • drop してから同名の列を add すると、古いデータが復活する
    • 位置で識別している場合、列の順序を変えると値がずれる
  7. パーティションがユーザーに露出している。dt という文字列列を別に持ち、クエリでも WHERE dt = ... と明示しないとフルスキャンになる。粒度を日から時間に変えるにはテーブルの作り直しが必要
  8. 小さなファイル問題。細かい書き込みでファイルが増え、listing と読み取りがさらに遅くなる
  9. ファイル単位の統計がない。統計はパーティション単位でしかなく、しばしば古いので、ファイルのスキップはパーティション単位が限界

Hive ACID（2014年〜、Hive 3 で標準化）も解決を試みました。base／delta ディレクトリとコンパクションで更新を実現しましたが、Hive のトランザクションマネージャ前提で ORC 専用だったため、他のエンジンからは扱いにくいものでした。そこで、エンジンに依存しない解決が求められるようになります。

2.4解き方の分岐：3つのアプローチ（2012〜2017年）

アプローチ代表考え方
(A) 専用ストレージエンジンを作るHBase、Apache Kudu更新もスキャンも得意なサーバを作る
(B) クローズドなクラウド DWH に任せるRedshift、BigQuery、Snowflake全部ベンダーが面倒を見る
(C) ファイルの上にメタデータ層を作るHudi、Iceberg、Delta Lakeサーバを持たず、ファイルとメタデータの規約で解く

(A) Apache Kudu（Cloudera、2015年発表、2016年に Apache TLP）

当時の Hadoop 界隈には次のようなジレンマがありました。

  • HDFS ＋ Parquet：スキャンは速いが、更新できない
  • HBase：ランダムな読み書きは速いが、スキャンが遅い

リアルタイム分析にはこの両方が必要だったため、「ストリームは HBase に書き、定期的に HDFS へ移し、ビューでマージする」という Lambda アーキテクチャが使われていましたが、非常に複雑でした。

Kudu は「Fast Analytics on Fast Data」を掲げ、主キー付きの列指向ストレージで、行単位の insert／update／delete を数ミリ秒で行い、しかもスキャンも速いことを目指しました。主に Impala と組み合わせて使われます。

技術的には優れた設計でしたが、主流にはなりませんでした。よく挙げられる理由は次のとおりです。

  • 常駐サーバとローカルディスクが前提で、計算と保存が密結合している。クラウドの「オブジェクトストレージ＋計算の分離」という潮流と逆向きだった
  • データは Kudu の内部形式なので、Kudu API を経由しないと読めない（エンジン中立ではない）
  • 3重レプリケーション、リバランス、ノード障害対応といったクラスタ運用が必要
  • Hadoop／Cloudera のエコシステム自体が縮小した

ただし、Kudu の「base ＋ delta を書いて、後でコンパクションする」という発想は、OTF の Merge-on-Read（Hudi MoR、Iceberg の delete file、Delta の Deletion Vector、Paimon の LSM）として、オブジェクトストレージ上で再実装されています。Kudu は OTF の対照例として理解すると分かりやすいです（Cloudera CDP の中などで現役ではあります）。

(B) Snowflake などのクラウド DWH

Snowflake（2014年頃に登場）は、データを S3 上のイミュータブルな独自形式の列指向ファイル（micro-partition）として保存します。そして「どの micro-partition がテーブルを構成するか」と列ごとの min/max 統計を、トランザクショナルなメタデータストア（FoundationDB）に持ちます。更新は「新しいファイルを書いてメタデータを切り替える」方式で、タイムトラベルやゼロコピークローンもここから実現されています。

POINT

これは OTF とほぼ同じ発想です。違いは、すべてがクローズドなことです。形式は非公開で、Snowflake のエンジンからしか読めません。見方を変えると、OTF は Snowflake 的なアーキテクチャをオープン仕様にしたものとも言えます。

(C) 三大 OTF の誕生

発祥動機
Apache HudiUber、2016年（2017年 OSS、2020年 Apache TLP）MySQL や Kafka からデータレイクへの反映に数時間〜1日かかっていた。upsert と増分処理（変わったレコードだけを処理する）が欲しかった。名前は Hadoop Upserts Deletes and Incrementals の略
Apache IcebergNetflix、2017年（Ryan Blue、Dan Weeks。2018年 Apache incubator、2020年 TLP）S3 上の巨大な Hive テーブルで、listing の遅さ、結果整合性による正しさの問題、スキーマ進化のバグに苦しんでいた。テーブルの正しさとスケールを根本から解決する仕様を、最初からエンジン非依存の「仕様先行」で設計した
Delta LakeDatabricks、2017年に社内製品化 → 2019年4月 OSS、同年10月 Linux FoundationSpark ユーザーのデータレイクが「データの沼（data swamp）」になっていた。ジョブが失敗するとデータが壊れ、ストリーミングとバッチの整合が取れない。Spark Structured Streaming と密に統合された

興味深いのは、3つの組織がほぼ同時期に、独立して、同じコア設計にたどり着いたことです。コア設計とは「イミュータブルなファイル＋テーブルを構成するファイルのログ＋アトミックなコミット」です。オブジェクトストレージと列指向ファイルという前提から見ると、これが自然な解だったことがうかがえます。

2.5Lakehouse の提唱（2020〜2021年）

Databricks は Delta Lake の論文（VLDB 2020）と Lakehouse 論文（CIDR 2021）で、次のように主張しました。

  • 従来は「データレイク（生データ・ML 用）→ ETL → DWH（BI 用）」という2層構成だった。この構成には、データの二重持ち、鮮度の遅れ、コスト、ロックイン、ML から DWH のデータを効率よく読めないといった問題がある
  • OTF（ACID とメタデータ）に、キャッシュ、データレイアウトの最適化、高速なエンジンを組み合わせれば、データレイク上で直接 BI まで賄える
  • オープン形式のデータを1コピーだけ持ち、BI、ML、ストリーミングといった複数のワークロードで共有する

2.6フォーマット戦争と収束（2022年〜）

時期出来事

2026年時点の勢力図（筆者の見立て）は次のとおりです。

  • Iceberg は、エンジン間・ベンダー間の相互運用の事実上の標準になった。Snowflake、AWS（Athena／EMR／Glue／Redshift／S3 Tables）、BigQuery、Databricks（Unity Catalog 経由）、Trino、Flink、DuckDB、ClickHouse、PyIceberg、iceberg-rust など、対応先が圧倒的に広い
  • Delta Lake は、Databricks と Microsoft Fabric の内部で支配的で、導入実績も大きい
  • Hudi は、upsert の多い CDC パイプラインで根強い
  • Paimon（Flink Table Store から発展、2024年に Apache TLP）は、Flink 中心のストリーミング upsert で使われる
  • 争点は「どのフォーマットか」から「どのカタログか」に移った。コミットの調停、アクセス制御、認証情報の払い出しはカタログが握るためで、ロックインの源泉もカタログ側に移りつつある
