03

仕組み：OTF は何をしているのか

3.1共通の原理

三大 OTF は細部こそ違いますが、土台にある原理は共通です。

  1. データファイルはイミュータブル（一度書いたら変更しない）
  2. テーブルの状態（有効なファイル集合、スキーマ、パーティション定義、統計）をメタデータに明示的に記録する
  3. 変更は「新しいファイルを書く → 新しいメタデータ（スナップショット）を作る → 現在版をアトミックに切り替える」という手順で行う
  4. 切り替えは楽観的同時実行制御（OCC）。競合したら確認してリトライする
  5. 読み手はある時点のスナップショットを固定して読む。つまり MVCC とスナップショット分離

この仕組みから、次の性質がそのまま得られます。

  • 原子性：途中で落ちても、どこからも参照されないファイルが残るだけ。後で orphan file として掃除する
  • 分離性：読み手は v41 を最後まで一貫して読める
  • タイムトラベル：v30 のメタデータが残っていれば v30 を読める
  • listing 不要：ファイルのパスはメタデータに書かれている
  • データスキップ：ファイルごとの min/max がメタデータにあるので、ファイルを開かずに読む対象を絞り込める
POINT

ストレージに求めるアトミック操作は1つだけです。Delta Lake ならログファイルの「put-if-absent」、Iceberg ならカタログ上の「ポインタの compare-and-swap（CAS）」です。それ以外は、普通の PUT と GET で済みます。

3.2Delta Lake の内部

Delta テーブルのディレクトリ構成 
orders/
├── _delta_log/
│   ├── 00000000000000000000.json
│   ├── ...
│   ├── 00000000000000000040.checkpoint.parquet   ← 既定では10コミットごと
│   ├── 00000000000000000041.json
│   ├── 00000000000000000042.json
│   └── _last_checkpoint
├── part-00007-a1b2.snappy.parquet
└── part-00012-c3d4.snappy.parquet

コミットファイルは「アクション」を1行1件で並べた NDJSON です（下の例は見やすさのため改行しています）。

_delta_log/00000000000000000042.json 
{"commitInfo":{"operation":"MERGE","readVersion":41,"isolationLevel":"WriteSerializable", ...}}
{"remove":{"path":"part-00007-a1b2.snappy.parquet","deletionTimestamp":1717200000000,"dataChange":true}}
{"add":{"path":"part-00012-c3d4.snappy.parquet","size":104857600,"partitionValues":{},"dataChange":true,
        "stats":"{\"numRecords\":812345,\"minValues\":{\"order_id\":1000},\"maxValues\":{\"order_id\":9999},\"nullCount\":{\"order_id\":0}}"}}
  • スナップショットの再構成：最新のチェックポイント（v40）に 41.json、42.json を順に適用する。その結果「add されていて、remove されていないファイル集合」が v42 のテーブルになる
  • 排他制御：N+1.json を put-if-absent で作れた writer が勝つ。HDFS、ADLS、GCS はこれをネイティブにできるが、S3 は長らくできなかったため、DynamoDB を使う LogStore などで補っていた。2024年の S3 条件付き書き込みで、この制約は解消に向かっている
  • カタログ管理テーブル：Delta Lake 4.0（2025年9月）では、コミットの調停をファイルシステムではなくカタログに任せる「カタログ管理テーブル」（table feature 名は catalogManaged）がプレビューとして入った。複数クラウド・複数エンジンからの書き込みを想定している
  • その他の主な機能
    • プロトコルバージョンと table features：リーダー／ライターが対応すべき機能を、テーブル側で宣言する
    • Deletion Vector：削除した行を RoaringBitmap で記録し、ファイルの書き直しを避ける
    • Column Mapping：物理列名と論理列名を分離し、rename／drop を安全にする
    • Change Data Feed：行レベルの変更履歴を出力する
    • Liquid Clustering：固定のパーティションと Z-order に代わる、後から変更できるクラスタリング
    • txn アクション：ストリーミング書き込みを冪等にし、exactly-once を実現する

3.3Apache Iceberg の内部

コミットは、新しい metadata.json を書いてから、カタログで「旧パス → 新パス」を CAS で切り替える操作です。具体的な実装はカタログごとに違います。

  • Hive Metastore：ロックを取って ALTER TABLE
  • JDBC カタログ：UPDATE … WHERE metadata_location = 旧パス
  • REST カタログ：サーバ側が要件（requirements）を検証して適用する

クエリ計画は多段のプルーニングになっています。

  1. manifest list のパーティション範囲を見て、manifest ごとスキップする
  2. manifest の列統計を見て、データファイル単位でスキップする
  3. Parquet の footer とページインデックスを見て、Row Group やページの単位でスキップする

これで、数百万ファイルあるテーブルでも、listing なしで数秒以内に計画を立てられます。

Iceberg の設計上の特徴は、次の3点です。

① 列を ID で識別する（安全なスキーマ進化）

各列に一意の field ID を振り、Parquet ファイル側にも ID を埋め込みます。rename はメタデータ上の名前を変えるだけで済みます。drop した列と同名の列を新しく add しても別の ID になるので、古いデータが復活しません。第2章で挙げた事故は、構造的に起きなくなります。

② Hidden Partitioning と Partition Evolution

Hive 流と Iceberg の比較（Spark SQL） 
-- Hive 流：パーティション用の列を自分で持ち、クエリでも明示が必要
CREATE TABLE orders (order_id BIGINT, ts TIMESTAMP, amount DECIMAL(10,2))
PARTITIONED BY (dt STRING);
SELECT sum(amount) FROM orders
WHERE ts >= '2024-06-01' AND ts < '2024-06-02'
  AND dt = '2024-06-01';               -- 書き忘れるとフルスキャン

-- Iceberg：変換関数でパーティションを定義する。ユーザーは ts で絞るだけでよい
CREATE TABLE orders (order_id BIGINT, ts TIMESTAMP, amount DECIMAL(10,2))
USING iceberg
PARTITIONED BY (days(ts), bucket(16, order_id));
SELECT sum(amount) FROM orders
WHERE ts >= '2024-06-01' AND ts < '2024-06-02';   -- 自動でプルーニングされる

-- 後から粒度を変える。既存データの書き直しは不要で、古いファイルは古い仕様のまま共存する
ALTER TABLE orders DROP PARTITION FIELD days(ts);
ALTER TABLE orders ADD  PARTITION FIELD hours(ts);

変換関数には identity、bucket[N]、truncate[W]、year、month、day、hour などがあります。パーティションは「データの物理配置の最適化」であって、利用者が意識する論理的な列ではない、というのが Iceberg の考え方です。

③ ブランチとタグ

スナップショットに名前を付けて分岐できます。「ブランチに書く → 品質を検査する → main に反映する」という Write-Audit-Publish（WAP）パターンが組めます。Project Nessie を使えば、Git のように複数のテーブルをまとめてブランチ管理することもできます。

このほか、行レベル削除は format v2 の delete file（位置指定の position delete と、値指定の equality delete）で導入され、v3 では Delta と同じ発想の Deletion Vector（Puffin ファイルに格納するビットマップ）に置き換わりました。v3 は行ごとの ID と最終更新のシーケンス番号を追跡する行リネージも導入し、増分処理や CDC に使えるようになっています。

3.4Apache Hudi の内部

  • .hoodie/ にタイムラインを持つ。commit、deltacommit、compaction、clean、rollback などの instant が、requested → inflight → completed と遷移する
  • レコードキーとインデックス（bloom、bucket、メタデータテーブル内の record-level index など）で「この key はどのファイルにあるか」を引けるため、upsert が効率的。ここが他の OTF との大きな違い
  • 2種類のテーブル型
    • Copy-on-Write：更新時にファイルを書き直す。読みは速い
    • Merge-on-Read：base の Parquet に、更新を log ファイル（Avro）として追記し、読むときにマージする。書きが速い。後でコンパクションする（Kudu の base ＋ delta とよく似た構造）
  • 増分クエリ：「コミット X 以降に変わったレコードだけ」を読める
  • メタデータテーブル（内部的な MoR テーブル）にファイル一覧や統計、索引を持ち、listing を避ける
  • コンパクション、クラスタリング、クリーニングといったテーブルサービスを、書き込みと同時（inline）にも非同期にも動かせる
  • Hudi 1.0（2024年12月）では、LSM 構造のタイムライン、セカンダリインデックス、ロックを取らずに並行書き込みできる制御（NBCC）などが入った

3.5Apache Paimon（補足）

Paimon は、バケットごとに LSM ツリーを持つ、ストリーミングファーストのテーブルフォーマットです。Flink からの高頻度な upsert に強く、changelog（変更ストリーム）を生成したり、partial-update や集約といったマージエンジンを選べたりします。データベースの LSM ストレージエンジン（RocksDB など）の考え方を、オブジェクトストレージ上のテーブルに持ち込んだもの、と捉えると理解しやすいです。

3.6行レベル更新の2方式：CoW と MoR

Copy-on-Write（CoW）Merge-on-Read（MoR）
更新・削除の方法該当行を含むファイルを丸ごと書き直す削除マーカーや差分を別に書く
書き込みコスト大（書き込み増幅）小
読み取りコスト小大（マージが必要）
必要なメンテナンス少ないコンパクションが必須
実装例Delta（既定）、Iceberg、Hudi CoWIceberg v2 の position／equality delete、v3 と Delta の Deletion Vector、Hudi MoR、Paimon
CDC を MERGE で反映する例（Delta ／ Iceberg 共通の Spark SQL） 
MERGE INTO orders t
USING orders_cdc s ON t.order_id = s.order_id
WHEN MATCHED AND s.op = 'D' THEN DELETE
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;
